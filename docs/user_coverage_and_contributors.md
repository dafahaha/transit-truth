# 用户覆盖与贡献者生态设计

> 本文档解决两个关键问题：1）没有GitHub账号/不能访问外网的用户如何使用和贡献；2）如何设计分层贡献者体系，避免价值稀释。

---

## 一、多渠道用户覆盖方案

### 1.1 用户分层

| 用户类型 | 特征 | 占比估计 | 覆盖策略 |
|---|---|---|---|
| 技术用户 | 有GitHub账号，能访问外网，会用命令行 | 20% | GitHub原生流程 |
| 普通国内用户 | 没有GitHub账号，访问GitHub不稳定 | 60% | 国内镜像+多渠道贡献 |
| 非技术用户 | 不会用命令行，只想用工具 | 20% | 在线Demo+一键操作 |

### 1.2 多渠道贡献方式

#### 渠道1：GitHub Issue（技术用户）
- **方式**：提交GitHub Issue，包含审计结果JSON
- **优势**：可追溯、可审核、与代码仓库集成
- **适用**：技术用户、有GitHub账号的用户

#### 渠道2：在线表单（普通用户）
- **方式**：在在线Demo中加入"一键贡献"按钮，用户点击后自动提交到后端
- **后端部署**：
  - 主后端：部署在Vercel/Render（国内可访问）
  - 备用后端：部署在国内云函数（阿里云/腾讯云）
- **优势**：用户不需要GitHub账号，一键完成
- **适用**：所有用户

#### 渠道3：邮件提交（最简单）
- **方式**：用户把审计结果JSON发送到指定邮箱（contribute@transit-truth.xxx）
- **处理**：定期人工审核，批量导入数据库
- **优势**：零门槛，任何人都能贡献
- **适用**：非技术用户、不方便用其他方式的用户

#### 渠道4：社区提交（运营驱动）
- **方式**：
  - 微信群/QQ群：用户在群里发审计结果，管理员定期收集
  - 知乎/V2EX评论区：用户在文章评论区发结果
  - Gitee Issues：国内用户通过Gitee提交
- **优势**：利用现有社区流量，降低贡献门槛
- **适用**：社区活跃用户

#### 渠道5：API批量提交（高级用户）
- **方式**：提供REST API，用户可以批量提交审计结果
- **认证**：API Key（不需要GitHub账号，邮箱注册即可）
- **优势**：适合批量贡献、自动化工具集成
- **适用**：高级用户、第三方工具开发者

### 1.3 国内可访问的在线Demo

#### 方案A：多平台部署（推荐）
- **GitHub Pages**：https://dafahaha.github.io/transit-truth/（国际用户）
- **Gitee Pages**：https://dafahaha.gitee.io/transit-truth/（国内用户）
- **Vercel**：https://transit-truth.vercel.app/（全球加速，国内可访问）
- **Netlify**：https://transit-truth.netlify.app/（备用）

#### 方案B：离线版本
- 用户下载 `index.html` 文件，本地双击打开
- 所有功能纯前端实现，不需要后端
- 文件大小：55KB，秒下载

#### 方案C：Docker镜像
- 用户本地部署：`docker run -p 8000:8000 dafahaha/transit-truth`
- 适合企业用户、需要批量审计的用户

### 1.4 数据同步机制

```
GitHub主仓库 ←→ 同步脚本 ←→ Gitee镜像仓库
     ↑                        ↑
     |                        |
  国际用户贡献             国内用户贡献
```

- **同步频率**：每天自动同步一次
- **同步内容**：代码、基准数据、排行榜数据
- **冲突处理**：以GitHub为主，Gitee的贡献通过PR同步到GitHub

## 二、分层贡献者体系

### 2.1 贡献类型划分

| 贡献类型 | 定义 | 贡献方式 | 信誉权重 |
|---|---|---|---|
| **代码贡献者** (Code) | 提交代码、修复Bug、开发新功能 | GitHub PR | ⭐⭐⭐⭐⭐ |
| **基准数据贡献者** (Data) | 提交模型基准数据（50+样本） | GitHub PR / 在线表单 | ⭐⭐⭐⭐ |
| **审计结果贡献者** (Audit) | 提交中转站审计结果 | 在线表单 / 邮件 / 社区 | ⭐⭐⭐ |
| **文档贡献者** (Doc) | 写文档、教程、翻译 | GitHub PR | ⭐⭐⭐⭐ |
| **社区贡献者** (Community) | 回答问题、组织活动、推广项目 | 社区活动 | ⭐⭐⭐ |

### 2.2 贡献等级制度

每个类型的贡献都有独立的等级：

| 等级 | 条件 | 徽章颜色 |
|---|---|---|
| **Bronze** (青铜) | 首次贡献 | 🟤 |
| **Silver** (白银) | 3次有效贡献 | ⚪ |
| **Gold** (黄金) | 10次有效贡献 | 🟡 |
| **Platinum** (白金) | 30次有效贡献 + 质量审核通过 | 🔵 |
| **Diamond** (钻石) | 100次有效贡献 + 核心贡献者认可 | 💎 |

**有效贡献定义**：
- 代码贡献：PR被合并
- 基准数据：数据通过质量审核（样本量≥50，采集方法正确）
- 审计结果：结果通过异常检测（不是明显错误或恶意数据）
- 文档贡献：PR被合并
- 社区贡献：管理员确认

### 2.4 信誉权重差异化

#### 审计结果信誉权重
```
最终信誉分 = 基础分 × 贡献者权重 × 数据质量分

贡献者权重：
- 代码贡献者 Platinum/Diamond：1.5x
- 代码贡献者 Gold：1.3x
- 基准数据贡献者 Gold+：1.2x
- 普通注册用户：1.0x
- 匿名用户：0.5x
- 新用户（<3次贡献）：0.3x

数据质量分：
- 完整审计（10+探针）：1.0x
- 快速审计（3探针）：0.7x
- 数据异常（需要人工审核）：0.0x（不计入排行榜）
```

#### 排行榜展示
- 每个审计结果显示贡献者类型和等级
- 高信誉贡献者的结果优先展示
- 低信誉贡献者的结果标记为"待验证"
- 匿名贡献者的结果需要人工审核后才公开

### 2.5 贡献者徽章系统

#### 徽章类型
| 徽章 | 图标 | 获得条件 |
|---|---|---|
| 代码贡献者 | 💻 | 至少1个PR被合并 |
| 基准数据贡献者 | 📊 | 至少1个模型基准数据被采纳 |
| 审计贡献者 | 🔍 | 至少3次有效审计 |
| 文档贡献者 | 📝 | 至少1个文档PR被合并 |
| 社区贡献者 | 🌐 | 管理员确认的社区贡献 |
| 早期贡献者 | 🚀 | 项目发布前30天内贡献 |
| 核心维护者 | 👑 | 项目维护团队成员 |

#### 徽章展示
- 贡献者名字旁边显示徽章图标
- 鼠标悬停显示徽章详情
- 可以叠加多个徽章
- 徽章按含金量排序（核心维护者 > 代码贡献者 > 数据贡献者 > ...）

## 四、关键设计原则

1. **降低贡献门槛，但不降低贡献质量**
   - 多渠道贡献让更多人能参与
   - 但所有贡献都需要质量审核
   - 低质量贡献不计入排行榜

2. **分层贡献者，避免价值稀释**
   - 代码贡献者和审计贡献者分开展示
   - 不同类型的贡献有不同的信誉权重
   - 徽章系统让贡献类型一目了然

3. **匿名贡献可接受，但信誉权重低**
   - 允许匿名用户贡献（保护隐私）
   - 但匿名贡献的结果需要人工审核
   - 匿名贡献者不进入贡献者展示页面

4. **国内用户全覆盖**
   - 多平台部署（GitHub/Gitee/Vercel）
   - 离线版本（下载HTML本地打开）
   - 多渠道贡献（不需要GitHub账号）

## 五、风险与应对

| 风险 | 应对措施 |
|---|---|
| 恶意用户刷审计结果 | 信誉权重差异化 + 异常检测 + 人工审核 |
| 贡献者等级通胀 | 严格的有效贡献定义 + 等级门槛递增 |
| 国内平台审查风险 | 内容中立，不涉及敏感话题，数据可审计 |
| 多平台数据同步冲突 | 以GitHub为主，定期同步，冲突人工处理 |
| 贡献者隐私保护 | 允许匿名贡献，邮箱不公开，数据加密存储 |
